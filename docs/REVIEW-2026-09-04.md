# FlowerMachine — code review, 2026-09-04

Eight reviewers with distinct lenses (real-time safety, threads and lifetimes, model and
persistence, controller state, UI logic, conformance to the locked architecture, the
Windows 10 target, efficiency) produced 52 findings, 37 after dedup by location. Each was
then given to three independent verifiers whose job was to REFUTE it. A finding is listed
here only if at least two failed to refute it: 26 survived, 11 were refuted.

**All 26 were fixed on 2026-09-04.** A twenty-seventh defect, found by hand while testing
the fixes and missed by every reviewer, is recorded at the end.

## 1. [critical] Unloading a hidden page frees no memory: publish(nullptr) retires the wrong ring slot

**Where:** `Source/Engine/SampleSlot.h:55` — category memory-lifetime, upheld by 3 of 3 refuters, raised by threading-lifetime, spec-conformance, efficiency-simplification

**What:** `publish()` writes the slot *after* the live one and retires only that slot's previous contents:

```cpp
const int writeIndex = nextIndex;   // always != current live index
retired.push_back (slots[(size_t) writeIndex]);   // keep whatever was there alive
slots[(size_t) writeIndex] = std::move (newData);
liveIndex.store (writeIndex, std::memory_order_release);
nextIndex = (writeIndex + 1) % numSlots;
```

The sample that is currently live sits in `slots[liveIndex]`, which is a *different* slot from `writeIndex`. So `publish (cartId, nullptr)` drops no reference to it at all: the decoded audio stays owned by the ring until 16 further publishes on that same cart wrap `nextIndex` back round to it. `Controller::unloadCart` (Source/Control/Controller.cpp:548) and `Controller::dropCart` (:563) use `publish (cartId, nullptr)` as the one mechanism for releasing a hidden page's RAM (ARCHITECTURE.md section 5, decision D5 - "Hidden pages are unloaded (`publish (nullptr)`)"). That mechanism releases nothing. The file is a verbatim copy of Svarog's, where slots are never unloaded, so the semantics were never exercised this way before.

**Failure:** A preset with two full pages; each cart is a 10 s stereo file at 48 kHz (~3.7 MB), i.e. the architecture's own 236 MB-per-page figure. The operator flips between tab 1 and tab 2 during a show. Each flip costs two publishes per cart (nullptr on hide, the fresh decode on show), so after 8 round trips each cart's 16-slot ring holds 8 complete decoded copies and nothing has been pruned: ~1.9 GB resident instead of the 236 MB D5 budgets. On the work PC (unknown, likely modest RAM) this either pages the audio buffers out - dropouts under the audio callback - or `data->audio.setSize()` in the pool job throws `std::bad_alloc`, which `ThreadPool::runNextJob` swallows in its `catch (...)`, so no result is ever delivered and those carts sit at "loading..." forever with no error shown.

**Suggested fix:** Add an `unload()` next to `publish()` that publishes nullptr and then moves every non-live ring slot into `retired` and nulls it, then prunes - it keeps the copied publish/acquire semantics intact (CLAUDE.md rule 5 forbids reinventing the class, not extending it). Call it from `Controller::unloadCart` and `dropCart` instead of `publish (cartId, nullptr)`. Alternatively hold the resident `SamplePtr` in the Controller and make the ring a non-owning hand-off.

## 2. [critical] Saving after a move rewrites relPath from the dead absolute path and permanently breaks every cart

**Where:** `Source/Model/Preset.cpp:206` — category data-loss, upheld by 3 of 3 refuters, raised by model-persistence, controller-state, efficiency-simplification

**What:** `Preset::save` recomputes every cart's `relPath` from the *stored* `path`, never from the file the cart actually resolved to:

```cpp
const auto absolutePath = cart[ids::path].toString();

if (juce::File::isAbsolutePath (absolutePath))
    cart.setProperty (ids::relPath, juce::File (absolutePath).getRelativePathFrom (folder), nullptr);
```

Nothing ever writes the resolved location back into `path`: `Preset::resolveFile` (lines 105-124) returns the file found via `relPath` but leaves the model untouched, and `Controller::loadCart` (Controller.cpp:520) only copies it into `status.file`. So once a preset has been moved together with its library — the exact scenario ARCHITECTURE.md section 3 and risk R2 build the whole relPath mechanism for, and the M2 verification step "move preset + library elsewhere and reopen" — `path` stays stale forever, and the first save rebases relPath onto that stale path.

**Failure:** Preset `D:/Radio/show.fmpreset`, cart `path="D:\Radio\lib\sweep.wav"`, `relPath="lib\sweep.wav"`. The operator copies the whole `D:/Radio` tree to `D:/Studio` and opens `D:/Studio/show.fmpreset`: the absolute path is gone, relPath resolves to `D:/Studio/lib/sweep.wav`, all 64 carts load, everything sounds right. The operator renames a page (or nudges one gain), the dirty dot appears, Ctrl+S. `save` sees `folder = D:\Studio` and writes `relPath = File("D:\Radio\lib\sweep.wav").getRelativePathFrom("D:\Studio") = "..\Radio\lib\sweep.wav"` — a path that points back at the folder that no longer exists. Both `path` and `relPath` are now dead. On the next launch every cart in the preset is `missing`, with no undo and no backup; the only recovery is Relocate, one cart at a time, 64 times.

**Suggested fix:** Resolve first, then rewrite both properties. Pass the document's current file into `save` (the Controller already holds it in `presetFile`) and per cart do `const auto resolved = resolveFile (cart, currentFile); if (resolved.existsAsFile()) { cart.setProperty (ids::path, resolved.getFullPathName(), nullptr); cart.setProperty (ids::relPath, resolved.getRelativePathFrom (folder), nullptr); }` — leaving both properties untouched when the cart resolves nowhere, so a missing cart keeps its original hints for a later Relocate.

## 3. [critical] Hiding a page frees no RAM: the slot ring keeps up to 8 decoded copies per cart

**Where:** `Source/Control/Controller.cpp:548` — category resource-leak, upheld by 3 of 3 refuters, raised by controller-state

**What:** `unloadCart` unloads a hidden page's cart with `engine.getCartEngine().publish (cartId, nullptr);` (Controller.cpp:548), relying on §5 "Hidden pages are unloaded (publish (nullptr))" to bound RAM to one page (D5). It does not. `SampleSlot::publish` (SampleSlot.h:55-56) only retires the content of the slot it is about to overwrite:

    retired.push_back (slots[(size_t) writeIndex]);   // keep whatever was there alive
    slots[(size_t) writeIndex] = std::move (newData);

With `nextIndex` advancing monotonically over 16 slots, publishing null writes the *next* slot; the slot holding the real sample is untouched and keeps a live `shared_ptr`. `prune()` can never free it, because `prune()` only scans `retired`. Every cart id has its own 16-slot ring, so the decoded audio of every page ever shown stays resident, and re-showing a page adds another copy rather than replacing one. Only after 16 publishes on that cart id (8 show/hide cycles) does the ring start evicting. `SampleSlot.h` is a verbatim copy of Svarog's, which is correct there because Svarog never unloads; FlowerMachine makes unloading a first-class operation.

**Failure:** A 2-page preset, page 1 = 40 carts of 30 s stereo (~230 MB decoded at 48 kHz), page 2 similar. Click tab 2: page 1's 40 carts get `publish(nullptr)`, page 2 decodes. Expected process RAM ~230 MB (D5); actual ~460 MB, because each of page 1's cart ids still holds its SampleData in `slots[]`. Alternate between the two tabs during a show: after 8 round trips each cart id's ring holds 8 decoded copies of the same file, ~1.8 GB, on a work PC of unknown (likely 4-8 GB) memory. `pruneAll()` on the Controller's 1 s timer frees nothing.

**Suggested fix:** Add a message-thread `SampleSlot::unload()` used by `unloadCart`/`dropCart`: publish null as now (flipping `liveIndex` onto a null slot), then move every other slot's `shared_ptr` into `retired` and `prune()`. Lifetime rule 5 is preserved — the retire list, not the audio thread, holds the last reference. This deviates from "SampleSlot copied verbatim" in CLAUDE.md, so flag it to the owner; the alternative that keeps the file untouched is to call `publish(nullptr)` `numSlots` times per cart at unload, which is worse.

## 4. [high] SampleLoader::cancel only bumps a counter; the cancelled decode still runs and blocks the new page

**Where:** `Source/Loading/SampleLoader.cpp:150` — category cancellation, upheld by 2 of 3 refuters, raised by threading-lifetime

**What:** `cancel()` is nothing but `++generations[(size_t) cartId];` and `request()` (line 144) does `pool.addJob (new Job (...), true)` without removing the cart's previous job. The generation number is only consulted in `deliver()` (line 158), i.e. after the job has already decoded and resampled the whole file. `juce::ThreadPool::pickNextJobToRun` hands out jobs in the order they were added, so cancelled jobs still occupy the pool's threads ahead of every job queued after them. Each stale job that completes also holds its full `SampleData` alive inside the pending `MessageManager::callAsync` payload (line 30) until the message thread drains it and drops it.

**Failure:** Page 1 holds 64 MP3s. The operator clicks tab 2 and immediately clicks back to tab 1. `Controller::setVisiblePage` cancels the 64 page-1 requests, queues 64 page-2 requests, then cancels those and queues 64 page-1 requests again. All 192 jobs run to completion on the pool's <=4 threads; the page-1 carts only begin decoding after 128 discarded decodes have finished, so a page that was resident a second ago shows "loading..." for seconds - directly against risk R3 ("carts become ready individually within tens of ms"). Transient RAM peaks at several pages' worth of decoded audio at once.

**Suggested fix:** Keep the last `Job*` per cart id (message thread only) and call `pool.removeJob (job, true, 0)` from `cancel()` and from `request()` before adding the replacement; additionally have `Job::runJob()` re-check a shared `std::atomic<int>` generation for its cart before starting the decode, so a job already picked up by a thread bails out at once.

## 5. [high] Right-click on a cart's STOP/LOOP/Gain controls fires the control instead of opening the cart menu

**Where:** `Source/UI/CartButton.cpp:91` — category input-handling, upheld by 3 of 3 refuters, raised by ui-logic

**What:** The three child controls sit in the bottom strip of every ready cart and swallow right-clicks, so `CartButton::mouseDown`'s `if (e.mods.isPopupMenu()) showMenu();` (line 205) is never reached for roughly the bottom third of the cell. Worse, JUCE acts on those right-clicks. `juce::Button::mouseDown` calls `updateState (true, true)` for any mouse button (juce_Button.cpp:470-482), so `isDown()` is set, and `Button::mouseUp` then calls `internalClickCallback (e.mods)` (juce_Button.cpp:484-502). A right-click therefore runs `stopButton.onClick = [this] { controller.stop (cartId); };` (line 86) and, because `loopButton.setClickingTogglesState (true)` (line 90), flips the toggle and runs `loopButton.onClick = [this] { controller.setLoop (cartId, loopButton.getToggleState()); };` (line 91). The gain knob is no better: `Slider::mouseDown` only opens its own menu when `menuEnabled` is set (it is not, that is the default), so a right-press falls into the drag branch (juce_Slider.cpp:862-902) and a right-drag edits the gain. ARCHITECTURE.md section 6 states "Right click = menu: Assign file..., Rename..., Colour..., Relocate... (when missing), Clear" for the cart, with no exception for the strip.

**Failure:** A ready, non-looping cart is playing on air. The operator right-clicks near the bottom of the cell intending "Rename...". The pointer is over LOOP: no menu appears, the loop flag turns on, `Controller::setLoop` writes `ids::loop` into the preset, `markDirty()` fires and the dirty dot appears. The next time that cart is triggered it never ends by itself; per D2 it also stops being cleared by other carts starting, so it plays until its own Stop or STOP ALL. Right-clicking a few pixels to the left instead stops the cart mid-jingle.

**Suggested fix:** Route popup-menu clicks on the children back to the cart: add the CartButton as a mouse listener on the three controls and open the menu on a right-press, or guard each `onClick` with `if (juce::ModifierKeys::getCurrentModifiers().isPopupMenu()) { showMenu(); return; }`. Also set `gainSlider.setPopupMenuEnabled (false)` explicitly and intercept its right-press.

## 6. [high] Clicks made while no audio device is open are queued and all fire at once when a device is picked

**Where:** `Source/Control/Controller.cpp:231` — category stale-command-queue, upheld by 3 of 3 refuters, raised by windows-deploy

**What:** `Controller::trigger` pushes into the command FIFO whenever the cart's status is `ready`, without any check that an output device exists:

    if (isValidCart (cartId) && statuses[(size_t) cartId].state == CartState::ready)
        engine.getCartEngine().push ({ Command::Type::play, (juce::uint16) cartId });

The only consumer of that FIFO is `CartEngine::render` (Source/Engine/CartEngine.cpp:88), which is reached solely from the device callback. With no device open the queue is never drained. Carts still reach `ready` in that state, because `Controller::targetSampleRate()` (Source/Control/Controller.cpp:578) falls back to `48000.0` when `engine.getSampleRate()` is 0 and `SampleLoader` decodes and delivers normally. `AudioEngine::stopAll()` (Source/Engine/AudioEngine.cpp:117) has the same problem, and the `bool` returned by `CommandFifo::push` — documented in Source/Engine/Commands.h:26 as "surfaced by the caller, never hidden" — is discarded at every call site.

**Failure:** On the work PC the Axia IP-Driver has not published its WDM endpoints yet when FlowerMachine starts (driver still coming up, or the saved device is gone and no default output exists), so `AudioDeviceManager::initialise` opens nothing. The last preset still reopens and the visible page decodes at the assumed 48 kHz, so all 40 carts show as ready. The operator clicks four carts, hears nothing, opens Settings and selects "Axia IP-Driver Out 1". `prepareToPlay` runs, then the first `render` drains all four queued `play` commands in one block: the fourth cart starts from frame 0 at full gain and the first three blip through their 5 ms release — unexpected audio on the output the instant the device is selected.

**Suggested fix:** Drain the FIFO in `CartEngine::prepare()` (it already retires every voice there) so nothing queued before the device started survives, and/or make `Controller::trigger`/`stop`/`stopAll` no-ops while `engine.getDeviceManager().getCurrentAudioDevice() == nullptr`. Also surface a failed `push` instead of dropping the return value.

## 7. [high] Renderer choice never reaches popup menus, alert windows or call-out boxes

**Where:** `Source/UI/Renderer.h:62` — category renderer-switch, upheld by 2 of 3 refuters, raised by windows-deploy

**What:** `applyToAllWindows` only touches windows that already exist at the moment it runs:

    for (int i = 0; i < desktop.getNumComponents(); ++i)
        if (auto* c = desktop.getComponent (i))
            applyTo (*c, choice);

and `Main.cpp:80` applies the choice once, to the main window's peer. Every peer created afterwards gets Direct2D unconditionally: in JUCE 8.0.12, `Component::createNewPeer` (juce_gui_basics/native/juce_Windowing_windows.cpp:4809) is `new HWNDComponentPeer { *this, styleFlags, (HWND) parentHWND, false, 1 }`, and `contextDescriptors` (same file, line 5639) is `contextDescriptorList<GDIRenderContext, D2DRenderContext>` — index 1 is "Direct2D". There is no global default and no automatic GDI fallback. `SettingsComponent::show` is the only place that re-applies (SettingsDialog.cpp:105); nothing re-applies for `PopupMenu::showMenuAsync` (CartButton.cpp:234, MainComponent.cpp:193, PageStrip.cpp:41), the `juce::AlertWindow`s created by every function in Dialogs.cpp, or the `juce::CallOutBox` colour picker (CartButton.cpp:296), all of which create their own top-level HWND.

**Failure:** The work PC's GPU driver cannot create a Direct2D device (risk R1), so the operator starts `FlowerMachine.exe --software-renderer`. The main window now paints. They right-click a cart to assign a file: `PopupMenu::showMenuAsync` creates a fresh peer with engine 1, the menu window never paints, and the click-through is invisible. Same for the File menu, for "Unsaved changes" on quit, and for every error dialog — the emergency switch leaves the app unusable in exactly the case it exists for.

**Suggested fix:** Re-apply after each window-creating call — `PopupMenu::showMenuAsync` and `CallOutBox::launchAsynchronously` create their window synchronously, so `renderer::applyToAllWindows (renderer::effective (settings))` immediately afterwards catches them — and/or run a low-rate timer that walks `juce::ComponentPeer::getNumPeers()` / `getPeer(i)` while the software renderer is selected.

## 8. [medium] Stale play commands and a pending test-tone trigger fire when a device (re)starts

**Where:** `Source/Engine/CartEngine.cpp:64` — category stale-state, upheld by 3 of 3 refuters, raised by rt-safety

**What:** `CartEngine::prepare()` resets voices (`retire (voice)`, `voiceCount.fill (0)`, `cart.playing.store (false)`) but never clears `commands`; `render()` then drains whatever accumulated: `for (int handled = 0; handled < COMMAND_FIFO_SIZE && commands.pop (command); ++handled) handle (command);`. Nothing consumes the FIFO while no device callback runs, yet the controller keeps producing: with no device `Controller::targetSampleRate()` falls back to 48000, carts decode and become `ready`, and `Controller::trigger()` pushes `play` for every click. The same applies to `AudioEngine::TestTone::prepare()` (AudioEngine.cpp:13-23), which does not clear `triggerRequested` / `stopRequested`.

**Failure:** Launch with the saved Axia device absent and no usable default (initError set), open a preset, click three carts trying to get sound (three `play` commands queue, the FIFO is never drained), then open Settings and pick the device. `setAudioDeviceSetup` starts it, `prepare()` runs, and the first `render()` executes the three queued plays: the carts start on air seconds after the clicks (with D2 the last non-looping one plus every looping one keeps sounding). Same outcome when a running device drops (WASAPI `deviceSessionExpired`, `getSampleRate()` stays > 0 so carts stay triggerable) and the manager later opens the default device. If Test tone was pressed meanwhile, a 300 ms -12 dBFS burst also fires on the fresh device.

**Suggested fix:** Add `void clear() noexcept { fifo.reset(); }` to `CommandFifo` and call it from `CartEngine::prepare()` (the callback is stopped and prepare runs on the producer thread, so the reset is race-free); in `TestTone::prepare()` store `false` into both request flags.

## 9. [medium] flushAll is pushed on any device-manager change message while a cart is loading, cutting live voices without a ramp

**Where:** `Source/Control/Controller.cpp:430` — category spurious-flush, upheld by 3 of 3 refuters, raised by rt-safety

**What:** `handleDeviceChanged()` runs on every `AudioDeviceManager` change message (`AudioEngine::changeListenerCallback` -> `onDeviceChanged`). Its trigger is `if (status.state == CartState::loading || decodedAtOtherRate)` and it then does `engine.getCartEngine().push ({ Command::Type::flushAll, 0 });` and `loadCart (cartId);`. `AudioDeviceManager` broadcasts far more often than on a rate change: `audioDeviceListChanged()` ends with an unconditional `sendChangeMessage()` (any endpoint added/removed/default changed on the system), `midiDeviceListChanged()`, `setMidiInputDeviceEnabled()`. None of those restart the device, so voices are still sounding when `flushAll` retires them instantly (`retire` skips the DECLICK_MS release). When the device really restarted, `prepare()` has already retired every voice, so the flush is redundant there. The `loading` branch also bumps the generation of every in-flight decode, throwing the work away.

**Failure:** A looping bed plays from page 1. The operator switches to page 2: 64 MP3s enter `loading` for about a second. During that second Windows reports an endpoint event (a Bluetooth headset connects, a jack-sensing plug, a monitor's HDMI audio wakes, the default device changes) -> `audioDeviceListChanged` -> change message -> `handleDeviceChanged` finds `loading` carts -> `flushAll`: the bed cuts dead on air with a click, and the 64 decodes restart from scratch.

**Suggested fix:** Record the rate a load was requested at (`status.sampleRate = targetSampleRate()` in `requestLoad`, instead of zeroing it in `loadCart`) and re-request a `loading` cart only when that rate differs from `engine.getSampleRate()`, exactly like the `ready` case; drop the `flushAll` (prepare() already dropped the voices on a real device restart) or push it only when a mismatch was actually found. Optionally also compare `result.sample->sampleRate` with the device rate in `handleResult` and re-request there, which covers an in-flight decode regardless of change-message timing.

## 10. [medium] Turning Loop off inside the last DECLICK_MS of the file truncates the release: hard cut at the file end

**Where:** `Source/Engine/CartEngine.cpp:215` — category declick, upheld by 3 of 3 refuters, raised by rt-safety

**What:** The end-of-file check runs before the envelope: `if (voice.position >= length) { if (! loop) { retire (voice); return; } voice.position = 0; }`. The tail fade only starts when `! loop && ... && voice.position >= length - releaseFrames` is first observed (line 223) and always uses the full `envelopeStep`, so a voice that enters the tail window late (the loop flag was still set when it crossed `length - releaseFrames`) reaches `length` with the envelope still well above zero and is retired mid-ramp. This violates real-time rule 6 (every stop through the DECLICK_MS ramp).

**Failure:** 48 kHz, `releaseFrames` = 240. A 3 s loop plays; the operator clicks Loop off while the playhead is at `length - 100`. Next block: `loop` reads false, the tail release starts (envelope 1.0), 100 samples later `position == length` -> `retire` with envelope = 1 - 100/240 = 0.58 -> the output jumps from 0.58 x full-level loop content to silence: an audible click on air. Probability per toggle is DECLICK_MS / loop length (about 1 % on a 0.5 s loop).

**Suggested fix:** When the tail release begins with fewer than `releaseFrames` frames left, size the ramp to the remaining frames (a per-voice release step: `voice.envelope / jmax (1, (int) (length - voice.position))`), or let the voice wrap once more and release on the following pass, which also matches the documented 'toggling loop off lets the cart finish'.

## 11. [medium] With a 1-channel output the right channel of stereo carts is dropped instead of summed

**Where:** `Source/Engine/CartEngine.cpp:207` — category channel-handling, upheld by 2 of 3 refuters, raised by rt-safety

**What:** `renderVoice` maps sample channels 1:1 onto the first two output channels: `float* out0 = numOut > 0 ? output.getWritePointer (0, startSample) : nullptr; float* out1 = numOut > 1 ? output.getWritePointer (1, startSample) : nullptr;` and later `if (out0 != nullptr) out0[i] += in0[pos] * g; if (out1 != nullptr) out1[i] += in1[pos] * g;`. When the device exposes a single output channel (`numOut == 1`), `in1` is never read: a stereo file loses its entire right channel. The architecture specifies mono-in -> both outputs but the code has no stereo-in -> mono-out rule; silently discarding half the programme is wrong rather than a design choice. Outputs beyond 2 are simply left cleared, which is fine.

**Failure:** Output routed to a mono endpoint (a Bluetooth headset in hands-free mode, a mono USB/HDMI endpoint, an Axia output configured as a single channel). A sweeper whose voice-over sits in the right channel, or any hard-panned-right element, is inaudible; a file with content only in R plays as silence while the cart shows playing.

**Suggested fix:** For `numOut == 1` add `0.5f * (in0[pos] + in1[pos]) * g` into `out0` (for mono samples `in1 == in0`, so the sum reduces to the original signal).

## 12. [medium] Every file assignment decodes the same file twice

**Where:** `Source/Control/Controller.cpp:294` — category redundant-work, upheld by 3 of 3 refuters, raised by threading-lifetime, model-persistence, controller-state, windows-deploy, efficiency-simplification

**What:** The model listener reloads on either path property:

```cpp
if (property == ids::path || property == ids::relPath)
{
    if (pageOf (cartId) == visiblePage)
        loadCart (cartId);
```

but `Preset::setCartFile` (Source/Model/Preset.cpp:128-132) always writes `ids::path` and then `ids::relPath` as two separate `setProperty` calls, and `ValueTree::setProperty` fires a callback for each actual change. For a newly created cart both properties change, so `valueTreePropertyChanged` runs twice, `loadCart` runs twice, and `loader.request` is issued twice for the same file at generations N and N+1. `deliver()` throws the N result away. Every assignment path is affected: `assignFile`, drag-and-drop, `fillPageFromFolder`, and `relocateFile` whenever a preset file exists.

**Failure:** "Fill page from folder..." pointed at a folder of 64 MP3s creates 64 carts, each writing `path` then `relPath`: 128 decode jobs are queued and 64 finished results are discarded in `SampleLoader::deliver`. The page takes roughly twice as long to go ready, and (with the cancellation gap above) two full decoded buffers per cart are alive at the same time.

**Suggested fix:** Reload only on `ids::path`. For `ids::relPath`, re-resolve with `Preset::resolveFile` and reload only when the resolved `status.file` actually differs from the one already loaded/loading - that keeps the relocate-by-relative-path case working without a second decode on every assignment.

## 13. [medium] Decode job never polls shouldExit; quitting mid-decode hangs, then the pool thread is killed by force

**Where:** `Source/Loading/SampleLoader.cpp:108` — category shutdown, upheld by 3 of 3 refuters, raised by threading-lifetime

**What:** `Job::runJob` checks `shouldExit()` only after the entire decode (line 27) and once after the read in the resample branch (line 101). The whole-file read (`reader->read (...)`, lines 80 and 95) and the resampling loop

```cpp
for (int ch = 0; ch < numChannels; ++ch)
{
    juce::WindowedSincInterpolator interpolator;
    interpolator.reset();
    interpolator.process (ratio, native.getReadPointer (ch), data->audio.getWritePointer (ch), outFrames);
}
```

are uninterruptible. `~SampleLoader` (line 135) does `pool.removeAllJobs (true, 5000)`, which only sets `shouldStop` and waits; `juce::ThreadPool::~ThreadPool` then repeats `removeAllJobs (true, 5000)` and finishes with `stopThreads()` -> `Thread::stopThread (500)`, which on timeout logs "!! killing thread by force !!" and calls `killThread()` (TerminateThread on Windows).

**Failure:** A 25-minute bed at 44.1 kHz (allowed - `MAX_CART_MINUTES` is 30) is assigned to a cart on the visible page and the operator closes the window while it is being sinc-resampled to 48 kHz. Resampling ~72 M frames per channel with `WindowedSincInterpolator` takes far longer than the 10.5 s that the two `removeAllJobs` calls plus `stopThread (500)` allow. The app appears frozen for ~10 s and is then killed mid-allocation inside `AudioBuffer::setSize`/the CRT heap - leaked heap locks and, in the worst case, a crash or a corrupted exit code the operator sees as "FlowerMachine stopped working".

**Suggested fix:** Poll `shouldExit()` inside the per-channel loop (resample in chunks with `WindowedSincInterpolator`, which is stateful across calls) and read the file in blocks with a `shouldExit()` check per block. Then `removeAllJobs (true, 5000)` returns promptly and no thread is ever force-killed.

## 14. [medium] Settings window outlives AudioEngine at session end; ~AudioDeviceSelectorComponent touches freed memory

**Where:** `Source/Main.cpp:49` — category lifetime, upheld by 3 of 3 refuters, raised by threading-lifetime

**What:** `shutdown()` tears down `mainWindow`, `controller`, `loader`, `engine` - but nothing closes the Settings dialog, which is a separate desktop window owned only by the file-static `openDialog` SafePointer (Source/UI/SettingsDialog.cpp:11 and :102, `openDialog = o.launchAsync();`). `SettingsComponent` holds `AudioEngine& engine` and a `juce::AudioDeviceSelectorComponent deviceSelector` constructed from `engine.getDeviceManager()`; `AudioDeviceSelectorComponent::~AudioDeviceSelectorComponent` calls `deviceManager.removeChangeListener (this)` (juce_AudioDeviceSelectorComponent.cpp:1143-1145). `DialogWindow::LaunchOptions::launchAsync` enters modal state with `deleteWhenDismissed = true`, so that window is only deleted later by `DeletedAtShutdown::deleteAll()` -> `~ModalComponentManager` -> `stack.clear()`, which runs inside `shutdownJuce_GUI()` *after* `shutdown()` has already returned and freed the engine.

**Failure:** The operator has Settings open (checking the Axia output) when Windows starts a scheduled restart or the operator logs off. `WM_QUERYENDSESSION` is not gated on modality (juce_Windowing_windows.cpp:4261, unlike `WM_CLOSE` at :4249-4251), so it calls `systemRequestedQuit()` -> `quit()` -> `shutdown()`, which destroys the `AudioEngine` and its `AudioDeviceManager`. The modal-manager teardown then deletes the still-open DialogWindow, and `~AudioDeviceSelectorComponent` calls `removeChangeListener` on the freed `AudioDeviceManager` - a crash or silent heap corruption on exit.

## 15. [medium] systemRequestedQuit() quits without the unsaved-changes prompt

## 21. [medium] Resampler latency is not compensated: loops are not seamless, starts are late

**Where:** `Source/Loading/SampleLoader.cpp:112` — category audio-correctness, upheld by 3 of 3 refuters, raised by spec-conformance

**What:** The offline resample path runs the interpolator raw and takes its output as the whole file:

```cpp
const double ratio = sourceRate / targetRate;
const int outFrames = juce::jmax (1, (int) std::floor (sourceFrames / ratio));
data->audio.setSize (numChannels, outFrames);

for (int ch = 0; ch < numChannels; ++ch)
{
    juce::WindowedSincInterpolator interpolator;
    interpolator.reset();
    interpolator.process (ratio, native.getReadPointer (ch), data->audio.getWritePointer (ch), outFrames);
}
```

`Interpolators::WindowedSincTraits::algorithmicLatency` is 100 input samples (`C:\Program Files\JUCE\modules\juce_audio_basics/utilities/juce_Interpolators.h`), and `reset()` zero-fills the 200-entry `lastInputSamples` history. So output frame k is centred on input frame `k*ratio - 100`: the first `100/ratio` output frames ramp up out of the zeroed history, and the output ends 100 input samples short of the source. Nothing discards or compensates that latency — `outFrames` is computed purely from length.

ARCHITECTURE.md §4 and the CartEngine.h header comment both promise "a looping one wraps seamlessly". Whenever a file's rate differs from the device rate the wrap is not seamless. The code side should change.

**Failure:** A 44.1 kHz music bed is assigned to a cart, LOOP is on, and the Axia device runs at 48 kHz (ratio 0.91875). The decoded buffer begins with ≈109 frames (2.3 ms) fading up from silence and ends ≈2.3 ms of source material early. `CartEngine::renderVoice` wraps `voice.position` straight from `length` back to 0 with no crossfade, so every loop point produces roughly a 4.5 ms attenuation hole in the middle of a sustained bed — audible as a soft pulse once per loop, for as long as the bed runs. Same-rate files (the `approximatelyEqual` fast path at line 76) are unaffected, which is why it will not show up on a 48 kHz test file.

**Suggested fix:** Ask the interpolator for `outFrames + latencyOut` frames where `latencyOut = (int) std::ceil (juce::WindowedSincInterpolator::getBaseLatency() / ratio)`, into a scratch buffer, then copy from offset `latencyOut` into `data->audio`. Raise `padding` from 64 to at least `128 + latencyOut` input frames so the extra output frames still read inside `native`.

# Found during verification, not by the review

**Keyboard shortcuts never worked at all — Esc, Ctrl+S, Ctrl+O, Ctrl+N.**
`MainComponent::keyPressed` was only reachable when the focus happened to sit inside the
component. A key press is delivered to the focused component and then walks UP its parents
(`ComponentPeer::handleKeyPress`); with nothing focused the target is the window itself, and
the content component is its CHILD, so the chain never reaches it. That is the state right
after launch. Fixed by making `MainComponent` a `juce::KeyListener` registered on the window,
which puts it on the chain either way, and by grabbing focus once the window is shown.
Verified by driving real key events at the running app.
